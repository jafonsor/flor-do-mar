# PRD: Mouse Navigation and Projected Trajectories

Status: ready-for-agent

## Problem Statement

The current movement UI still thinks in heading buttons and sail presets. That made the first combat tracer bullet playable, but it does not match the tactical feel the game is moving toward: the player should command a ship by choosing where it should go, reading the projected trajectory, and deciding what speed it should carry after reaching the waypoint.

The tactical battle view also lacks the render primitives needed to show projected trajectories, speed rings, and debug overlays cleanly. The current flat mesh list and cube-only renderer will become a liability as soon as movement planning becomes visual.

## Solution

Replace player-facing heading and sail controls with mouse-issued navigation orders. Hovering over the battle view shows the selected projected trajectory from the ship's latest actual movement state to the reachable waypoint. Mouse down commits that reachable waypoint immediately so the ship starts maneuvering. If the player drags before release, the drag selects the active order's pending post-waypoint speed through a speed ring. If the waypoint has already cleared by release, the same gesture sets the ship's current target speed.

Movement is calculated by a kinematically constrained trajectory planner shared by simulation and preview. The planner accounts for current speed, acceleration, deceleration, rudder authority, yaw inertia, turn speed, ideal turn speed, arrival radius, and maximum speed. Preview mismatch with actual movement is a bug unless battle conditions change.

Upgrade the render layer toward a small 3D scene graph with quaternion-backed transforms and generic stroke primitives. Projected trajectories render as flat `StrokePath` geometry slightly above the water plane. Speed rings render as `RingStroke` geometry anchored to reachable waypoints. Stroke-like primitives are generated as triangle geometry, not WebGL line primitives.

## User Stories

1. As a player, I want hovering over the battle view to show the projected trajectory to a waypoint, so that I can see the consequence before committing.
2. As a player, I want the projected trajectory to respect the ship's current speed and turning limits, so that the preview teaches me what the ship can actually do.
3. As a player, I want unreachable/tighter-than-possible cursor positions to clamp to the nearest reachable waypoint, so that the UI never promises impossible movement.
4. As a player, I want mouse down to commit the reachable waypoint immediately, so that the ship starts turning as soon as I give the order.
5. As a player, I want dragging after mouse down to choose post-waypoint speed, so that movement and speed intent can be set in one gesture.
6. As a player, I want releasing after a drag to update the active order's post-waypoint speed, so that I can choose the speed the ship should carry after arrival.
7. As a player, I want releasing after the waypoint has already cleared to set current target speed, so that quick nearby orders still preserve the intended speed gesture.
8. As a player, I want a plain click to inherit arrival speed as post-waypoint speed, so that I can simply say "go there" without adjusting speed.
9. As a player, I want the speed ring to show arrival speed, selected speed, and maximum speed, so that I can understand how much speed the ship will have at the waypoint.
10. As a player, I want target speed to be continuous from stopped to maximum speed, so that speed control is not limited to three sail presets.
11. As a player, I want stopped ships to need forward movement before turning, so that losing way creates a real tactical consequence.
12. As a player, I want active navigation trajectories and speed rings to stay visible until arrival, so that I remember the order currently being executed.
13. As a player, I want hover replacement previews to appear alongside the active trajectory, so that I can compare the current order with a possible replacement.
14. As a player, I want new navigation orders to replace the active navigation order immediately, so that the ship responds to revised intent without queueing old paths.
15. As a player, I want broadside controls to keep working independently, so that firing does not interrupt movement orders.
16. As a player, I want setup and finished scenarios to block navigation input, so that planning only happens during active combat.
17. As a developer, I want projected trajectories generated by pure combat/domain logic, so that preview and simulation share the same movement model.
18. As a developer, I want trajectory samples to include position, heading, speed, yaw rate, and time/tick offset, so that rendering and tests can inspect the selected trajectory without planner internals.
19. As a developer, I want planner results to include requested waypoint, reachable waypoint, clamped status, and arrival speed, so that clamping and speed-ring behavior are explicit.
20. As a developer, I want the UI to receive only the selected trajectory, so that alternative planner internals never become player-facing.
21. As a developer, I want committed reachable waypoints to remain fixed after command time, so that recomputed projections do not move the goalpost.
22. As a developer, I want active projections recomputed from latest actual state each tick, so that the displayed remaining path reflects current movement state and hot reloads.
23. As a developer, I want yaw inertia represented in authoritative state and snapshots, so that planner prediction can start from the same movement state as simulation.
24. As a developer, I want rudder authority to be zero while stopped and rise linearly to ideal turn speed, so that first-version tuning is legible.
25. As a developer, I want the old minimum low-speed turn factor replaced, so that the model can express a ship getting stuck without way.
26. As a developer, I want enemy autopilot to issue normal navigation orders, so that non-player movement proves the same model works for any ship.
27. As a developer, I want the first enemy autopilot to orbit around its starting position, so that there is visible non-player movement without complex AI.
28. As a developer, I want enemy trajectory and speed ring overlays gated by a debug checkbox, so that I can inspect autopilot behavior without making it permanent player UI.
29. As a developer, I want the debug checkbox in the engagement setup overlay to apply immediately, so that debug rendering can be toggled without relaunching.
30. As a developer, I want mouse/DOM input translated through a client-only input adapter, so that future touch or alternate input sources can emit the same semantic UI intents.
31. As a developer, I want screen-to-world conversion kept with the battle view and camera layer, so that combat/domain never sees input-device details.
32. As a developer, I want the render layer to support a 3D scene graph, so that future 3D presentation is not blocked by 2D-only transforms.
33. As a developer, I want quaternion-backed rotations internally, so that future 3D transforms do not inherit Euler-only limitations.
34. As a developer, I want stroke-like primitives rendered as triangle geometry, so that trajectory and ring quality is not limited by WebGL line support.
35. As a developer, I want dashed trajectories represented as `StrokePath` style, so that battle scenes describe visual intent once and geometry generation owns the expansion.
36. As a developer, I want trajectory strokes and rings slightly above the water plane for now, so that overlays remain visible without adding render order yet.

## Implementation Decisions

- Preserve command-based combat. Player movement intent is submitted as commands, not direct steering.
- Replace player-facing heading and sail buttons with the mouse navigation gesture.
- Keep broadside firing as explicit player buttons for this slice.
- Introduce navigation orders as movement commands that work for any ship, not only the player ship.
- A navigation order stores requested waypoint metadata for diagnostics, but the simulation uses the committed reachable waypoint.
- Committed reachable waypoint is fixed at command time. Hot reload and normal ticks recompute the path to that waypoint, not the waypoint itself.
- Active navigation order owns pending post-waypoint speed. Do not introduce a general queued-command scheduler or multi-waypoint queue.
- Target speed is continuous from stopped to maximum speed. The player can only set it through the speed-ring mouse gesture for now.
- Reverse movement is not a command. Commanded target speed is never negative.
- A stopped ship has no rudder authority. It must accelerate straight ahead until it has enough way to turn.
- Rudder authority rises linearly from zero at stopped to full authority at ideal turn speed.
- `turn_rate` is maximum yaw rate at full rudder authority.
- Add per-ship-type yaw acceleration. Ship-specific yaw handling may remain even if mass is modeled later.
- Store signed current yaw rate in authoritative ship state and expose it in snapshots.
- No waypoint means target yaw rate is zero; the ship eases out of turns according to yaw inertia.
- Arrival clears the waypoint and leaves target speed intent.
- Selected post-waypoint speed applies after arrival, not as an arrival-speed constraint.
- The kinematically constrained trajectory planner may use target yaw rates internally, but direct yaw-rate commands are deferred.
- The planner result exposes selected trajectory samples, requested waypoint metadata, reachable waypoint, clamped status, and arrival speed.
- Render exactly the points produced by the trajectory calculator for now. Do not smooth or interpolate the route in the renderer.
- If the planner hits a safety cap before arrival, treat it as a safety/test fallback, not as normal player-facing UI.
- Disabled ships clear or ignore navigation.
- Firing broadside does not affect navigation orders in this slice.
- The setup overlay blocks navigation input and pauses ticks.
- Scenario-finished state hides planning overlays and rejects navigation input.
- Active player trajectory and speed ring remain visible until arrival.
- Hover preview starts from the latest actual ship state, even when an active order exists.
- Active trajectory is recomputed each tick and shows remaining future path only. Do not add wake/history trails.
- Enemy orbit autopilot issues normal navigation orders around the enemy starting position with a fixed first-playable orbit radius.
- Enemy/autopilot trajectory and speed ring render only when the client debug flag is on. Debug defaults to on.
- Debug flag is client state, lives in the engagement setup overlay, applies immediately, and persists only for the current client session.
- Add a client-only input adapter from raw pointer input to semantic UI intents.
- Keep screen-to-world conversion with battle view/camera code.
- Upgrade the render layer to a lightweight 3D scene graph inspired by Three.js / React Three Fiber.
- Scene graph nodes include groups, meshes, stroke paths, and ring strokes.
- Internal transform composition uses matrices and quaternion-backed rotations. Euler-style convenience APIs may come later.
- `StrokePath` and `RingStroke` are flat generated triangle geometry in scene space, not camera-facing billboards.
- Stroke-like primitives are not WebGL lines and should not be named as such.
- Stroke/ring geometry is generated CPU-side in Haskell for now and rebuilt when trajectory/style/camera-scale inputs change.
- Use small Z offsets to keep trajectories above water. Defer explicit render order.

## Testing Decisions

- Test behavior at the highest seams already present: pure combat tick transition, local Combat API, snapshot conversion, and render-scene conversion.
- Add pure planner tests for reachable waypoint selection, clamping, arrival speed, zero-speed rudder authority, yaw inertia, and fixed committed waypoint behavior.
- Add tests that preview samples match simulation movement for the same initial state and navigation order.
- Add tests that mouse-down navigation commits immediately while drag/release only updates pending post-waypoint speed.
- Add tests that if the waypoint clears before release, the release speed applies as current target speed.
- Add tests that new navigation orders replace active navigation orders instead of queueing paths.
- Add tests that broadside commands do not clear or change navigation orders.
- Add tests that disabled ships clear or ignore navigation.
- Add local Combat API tests for submitting navigation orders, observing active order state, advancing ticks, and seeing snapshots expose yaw rate and navigation state.
- Add hot reload tests that active reachable waypoint is preserved while projection/movement behavior updates from new physics.
- Add setup-state/client-state tests for debug flag default-on behavior, immediate toggle behavior, and setup overlay blocking navigation input.
- Add enemy autopilot tests proving orbit behavior issues normal navigation orders around the starting position.
- Add render-scene tests for active trajectory, hover trajectory, speed rings, debug enemy overlays, and absence of planning overlays in finished/setup states.
- Add render primitive tests for scene graph traversal, quaternion-backed transform composition, and flat stroke/ring geometry generation.
- Avoid browser DOM tests unless interaction state is extracted into pure models. Prefer testing pure input-intent translation and render scene output.
- Manual verification should include hovering, click-to-turn, drag-to-set-speed, clamped tight turns, stopped-ship straight-ahead acceleration, debug overlay toggle, and enemy orbit movement.

## Out of Scope

- Multiple queued waypoints.
- A general command scheduler.
- Direct yaw-rate player commands.
- Direct helm/manual steering.
- Keyboard modifiers for navigation.
- Right-click navigation behavior.
- Touch input design beyond keeping the input adapter extensible.
- Turn-induced speed bleed.
- Rudder stall.
- Wind/current movement effects.
- Reverse movement commands.
- Crew quality affecting movement execution.
- Wake/history trails.
- Collision physics.
- Render order/depth sorting for overlays.
- GPU-side stroke tessellation.
- Full AI combat tactics beyond the first orbit autopilot.
- Persisting debug setting beyond the current browser session.

## Further Notes

- This PRD follows ADR-0002, which records the shared navigation projection decision.
- This PRD follows ADR-0003, which records the 3D render scene graph decision.
- The old hot-reloadable boat physics work remains a prerequisite foundation, especially configured speed, acceleration, deceleration, turn rate, and hot reload behavior.
- The first implementation should prefer clear seams over clever optimization. The trajectory planner can become more mathematically sophisticated internally without changing the command, snapshot, or render-facing contracts.
